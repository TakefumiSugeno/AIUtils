# /rfp-init: 要求・要件定義およびプロジェクト初期化スキル

## 1. 目的と役割
ユーザから提示された「アプリのアイデア」や「質疑応答の回答」を構造化して `request.md`（要件定義書）を作成し、`D:\programming\repos\[プロジェクト名]` 配下に仕様書駆動開発（Specification-Driven Development: SDD）に準拠した初期リポジトリ環境および `AGENTS.md`（CLAUDE.md）を一括構築する。

---

## 2. 実行手順・ワークフロー

### Step 1: 要求ヒアリングとプロジェクト名の特定
1. ユーザから提供されたインプット（アイデア、背景、Q&A等）を解析する。
2. アプリケーション名（英数字・PascalCaseまたはkebab-case）を決定またはユーザに確認する。
   - ルートパス: `D:\programming\repos\[AppName]`

### Step 2: ワークスペースおよびディレクトリ構造の作成
以下のディレクトリ構成を対象リポジトリ内に作成する。

```text
D:\programming\repos\[AppName]/
├── .git/
├── AGENTS.md                 # 開発工程・運用ルール
├── request.md                # 要件定義ドキュメント（AIへの入力原典）
├── doc/
│   ├── spec.md               # システム仕様書（初期空ファイルまたは骨子）
│   ├── design_detail.md      # 詳細設計書（初期空ファイルまたは骨子）
│   ├── mock/                 # UIモック・ワイヤーフレーム配置用
│   ├── tasks/
│   └── work/                 # 一時作業・バグ管理用
├── src/                      # ソースコード
└── test/                     # テストコード
```

### Step 3: `request.md` の生成
以下のテンプレートに基づき、ユーザの入力内容を漏れなく構造化して配置する。

```markdown
# 要求・要件定義書 (request.md)

## 1. プロジェクト概要
- **プロジェクト名**: [AppName]
- **背景・目的**: [なぜこのアプリを作るのか、解決したい課題]
- **ターゲットユーザー**: [想定利用者]

## 2. コアコンセプト・提供価値
- [アプリが提供する主要な体験・価値]

## 3. 主要機能要件 (Functional Requirements)
- **F-01 [機能群名]**:
  - [要求詳細・ユースケース]
- **F-02 [機能群名]**:
  - [要求詳細・ユースケース]

## 4. UI/UX・モック要件 (UI/UX Requirements)
- **画面構成・主要導線**: [想定画面一覧や画面遷移]
- **UIモック対象**: [モック作成が必要な画面・プロトタイプ形式 (HTML/CSS, Mermaid, ASCII等)]

## 5. 非機能要件・技術制約 (Non-Functional Requirements)
- **想定言語・フレームワーク**: [未定または検討中 / 例: 検討中の候補技術]
- **品質・テスト要件**: [TDD必須、単体テストカバレッジ目標等]
- **実行環境・プラットフォーム**: [OS, Web, デスクトップ, CLI等]

## 6. スコープ定義
- **In Scope (初期開発 / MVP対象)**:
  - [初期リリースで実装する機能・UIモック一覧]
- **Out of Scope (将来課題 / 今回のスコープ外)**:
  - [今回は対応しない機能・仕様]

## 7. インプットログ・質疑応答記録
- **Q**: [質疑内容]
- **A**: [ユーザ回答]
```

### Step 4: `AGENTS.md` の生成
プロジェクトルートに以下のエッセンスを反映した `AGENTS.md` を作成する。

```markdown
# AGENTS

## 構成

- `request.md`
  - 要件定義ドキュメント（AIへのインプット原典）
- `doc/`
  - 仕様書などのドキュメントのルートディレクトリ
- `doc/spec.md`
  - システム仕様書
- `doc/design_detail.md`
  - 詳細設計書
- `doc/mock/`
  - UIモック・ワイヤーフレーム・画面プロトタイプ配置ディレクトリ
- `doc/tasks/`
  - タスク管理ドキュメントの配置ディレクトリ
- `doc/tasks/YYYYMMDD-HHMMSS_[タスク概要]/tasks.md`
  - 未着手タスクごとに独立作成される個別のタスク管理ファイル
- `doc/tasks/YYYYMMDD-HHMMSS_[タスク概要]/reviews.md`
  - 該当タスクに関するサブエージェント批判的レビュー記録ドキュメント
- `doc/work/`
  - 開発に必要なテンポラリのディレクトリ（bugs.md 等のバグ管理）
- `src/`
  - ソースコードのルートディレクトリ
- `test/`
  - テストコードのルートディレクトリ（ソースコードと 1:1 対応）

## 運用ルール

### 基本原則: 仕様書駆動開発（Specification-Driven Development）

> **原則**: ドキュメントおよびUIモックを更新し、ユーザと合意してから実装に移行する。合意なしに実装を開始してはならない。

開発は必ず以下のフローで進める:

#### タスク管理・ディレクトリ運用方針

1. **未着手タスク別フォルダの作成・管理**:
   - 未着手のタスクごとに `doc/tasks/YYYYMMDD-HHMMSS_[タスク概要]/` 形式の命名規則で独立したフォルダを作成する。
   - フォルダ内に `tasks.md` (タスク計画・進捗) および `reviews.md` (批判的レビュー記録) を配置して管理する。

#### Step 1: タスク計画・レビューと合意

1. ユーザの指示に対して、対象タスクフォルダ `doc/tasks/YYYYMMDD-HHMMSS_[タスク概要]/tasks.md` に**構造化したタスク計画**を追加・更新する。
2. **サブエージェントによるドキュメントレビュー**:
   - 役割として「ユーザー」「SE/PG」のサブエージェントを呼び出し、該当タスクの `tasks.md` に対する批判的レビュー（漏れ、依存関係、テスト計画の欠落など）を実施し、結果を同一フォルダ内の `reviews.md` に記録する。
3. レビュー結果およびタスク計画の進め方をユーザーに提示し、**合意を得る**。
4. 合意後、該当タスクフォルダ内の `tasks.md` および `reviews.md` をフォーマットした上で commit する (ブランチ: `alpha`)。

#### Step 2: 仕様・設計・UIモックの更新・レビューと合意

1. `doc/spec.md`（システム仕様書）、`doc/design_detail.md`（詳細設計書）、および必要に応じて `doc/mock/`（UIモック・プロトタイプ）を作成・更新する。
2. **サブエージェントによるドキュメント・UIモックレビュー**:
   - 役割として「ユーザー」「SE/PG」のサブエージェントを呼び出し、仕様書・設計書・UIモックに対する批判的レビュー（仕様矛盾、画面遷移の不整合、設計漏れ、UX上の懸念、エッジケース、モデル定義の抜けなど）を実施する。
   - 指摘事項およびチェックリストを該当タスクフォルダ内の `reviews.md` に記録する。
3. 変更内容、UIモック、およびレビュー指摘への対応方針をユーザーに提示し、**仕様・画面・設計の合意を得る**。
4. 合意後、ドキュメント・UIモックをフォーマットした上で commit する (ブランチ: `alpha`)。

#### Step 3: 実装・検証およびレビューサイクル

1. 該当タスクフォルダ内の `tasks.md`、`doc/spec.md`、`doc/design_detail.md`、`doc/mock/` の内容に基づき、以下のサイクルで実行する:
   - **① エージェントによるタスク実行（実装・TDD） ＆ 自動フォーマット**:
     - ソースコードとテストコードは **1：1 のファイル構成** で作成する。
     - テスト先行 (Test First) で実装する。
     - **コードおよび各種ドキュメント（.md, UIモック等）のファイルを作成・更新した直後は、必ずプロジェクト定義の自動フォーマット処理を実行する。**
     - フェーズやタスクの最後のテスト実施時には、**実行結果のエビデンス**および**カバレッジレポート（Coverage Report）**を出力して確認・記録する。
     - **タスク実行完了後、成果物を commit する (ブランチ: `alpha`)**。
   - **② サブエージェントによる成果物レビュー**:
     - 役割として「ユーザー」「SE/PG」のサブエージェントを呼び出して実装成果物（コード・テスト・UI表示・動作結果）をレビューする。
     - 批判的レビュー結果およびチェックリストを該当タスクフォルダ内の `reviews.md` にチェックボックス形式（`- [x]` / `- [ ]`）で記録する。
     - **レビュー記録完了後、`reviews.md` 等をフォーマットした上で commit する (ブランチ: `alpha`)**。
   - **③ 指摘事項の対応方針記載 ＆ ユーザー合意**:
     - サブエージェントによるレビュー後、該当タスクフォルダ内の `reviews.md` に記載された指摘事項に対し、各項目の「対応方針・具体例・影響範囲」を `reviews.md` 内に追記・整理する。
     - ユーザーに対応方針を提示し、**必ずユーザーと対応方針について合意を得る**。合意後 `reviews.md` 等をフォーマットして commit する (ブランチ: `alpha`)。
   - **④ 指摘事項の修正・実装（TDD） ＆ 自動フォーマット**:
     - ユーザーと合意した対応方針に従い、テスト先行 (TDD) でコードおよびテストの修正・実装を進める。
     - 修正・変更を行ったファイル（コード・ドキュメント・UIモック）に対し自動フォーマット処理を実行する。
   - **⑤ ビルド・テスト・実行直前の自動フォーマット検証**:
     - ビルド、テスト、またはアプリケーションの実行を行う直前には、必ず自動フォーマット処理が適用済みであることを確認・実行する。
   - **⑥ ユーザー最終確認・合意**:
     - 成果物およびレビュー結果・テストエビデンス・動作画面をユーザーに提示し、最終確認・合意を得る。

#### Step 4: ドキュメントおよびUIモックの事後同期

1. 実装で仕様・設計・UIから変更が生じた場合は、`doc/spec.md`、`doc/design_detail.md`、`doc/mock/` に反映する。
2. 変更ファイルをフォーマットした上で commit する (ブランチ: `alpha`)。
3. **commit 直後、1つ前の履歴と比較して既存情報の欠落がないか確認し、欠落があれば復元すること**。

---

### 自動フォーマット定義（汎用方針）

採用技術スタック決定後、本セクションに使用するリンター・フォーマッタおよびコマンドを具体化する。原則として以下の種別ごとにプロジェクト標準ツールを設定・適用すること。

| 対象種別 | 適用タイミング | 整形方針・標準ツールの選定基準 |
| :--- | :--- | :--- |
| **ソースコード** | ファイル更新時 / コミット前 / テスト実行前 | 採用言語・フレームワークの公式推奨フォーマッタ（例: `Prettier`, `dotnet format`, `rustfmt`, `gofmt`, `black` 等） |
| **テストコード** | ファイル更新時 / コミット前 / テスト実行前 | ソースコードと同一のフォーマットルールを適用 |
| **ドキュメント (`.md`)** | ドキュメント更新時 / コミット前 | Markdown 標準フォーマッタ（例: `Prettier` 等）によるインデント・改行・表組みの統一 |
| **UIモック / Web資産** | モック・UI更新時 / コミット前 | HTML / CSS / JS / JSON 等の標準ウェブフォーマッタによる整形 |
| **設定・スクリプト** | 更新時 / コミット前 | JSON, YAML, 各種シェルスクリプト用静的解析・整形ツール |
```

### Step 5: Git初期化および初期コミット
1. `git init` を実行する（未初期化の場合）。
2. ブランチを `alpha` に切り替える（`git checkout -b alpha`）。
3. 生成したファイル一式をフォーマットし、初期コミットを行う。
   - コミットメッセージ: `docs: initialize project with request.md and AGENTS.md`

### Step 6: 完了報告
生成された `request.md` の概要とリポジトリ構成（`doc/mock/` 含む）をユーザに提示し、`Step 1`（タスク計画作成）の着手合意を求める。
