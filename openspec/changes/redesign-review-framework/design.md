# Design: redesign-review-framework

## Context

現行のレビュー機構は、タスクごとに20項目以上の表形式チェックリストを埋めさせる運用となっているが、事前実装指示（`config.yaml`）と同一内容の同語反復（トートロジー）となり、指摘がほぼゼロで形骸化している。
また、L2変更で1回あたり100〜200回以上のチェック項目生成が発生し、トークン・時間の浪費と認知的過負荷を生んでいる。
詳細は `proposal.md` 参照。

## Goals / Non-Goals

**Goals:**

- レビューチェックリストの表形式（`✅/❌/⚠️` 記号埋め）を廃止し、成果物別の挑戦的設問（Q&A形式）へ再設計する。
- 実装コードレビューにおいて、言葉の議論ではなく実際に例外や失敗を起こす破壊テストを実行して検証する Adversarial QA プロトコルを導入する。
- スクリプトで機械判定できる項目（フォーマット、静的解析、全テストPass、skip放置、カバレッジ）をLLMレビューから完全分離する。
- `verify-gate.ps1` / `verify-gate.sh` を新レビューフォーマットの機械検証に対応させる。
- `openspec-kit/`（配布用正本）と `openspec/`（本リポジトリ用）の整合性を維持する。

**Non-Goals:**

- Linterやテストランナーなどの外部静的解析ツールの独自開発。
- 人間によるPRレビュープロセスの廃止。

## Decisions

### 1. チェックリストの「表形式」から「成果物別 挑戦的Q&A」への転換

- **決定**: 各フェーズ・成果物に対応したチェックリスト（`checklist_propose.md`, `checklist_apply_impl.md`, `checklist_apply_test.md`, `checklist_archive.md`）を、20行以上の表形式から **3〜4つの挑戦的設問（悪魔の代弁者・ブラインド突合・特化ペルソナ）** へ刷新する。
- **代替案との比較**:
  - _案A: チェックリストの項目数を削るだけの表形式維持_ → 表形式である限り、AIが思考停止で `✅` を並べる悪癖が解消されないため不採用。
  - _案B: 今回採用のQ&A形式_ → 設問自体が「最も脆い箇所はどこか」「例外を起こす入力は何か」と問うため、自白・指摘が強制的に引き出される。

### 2. 実装コードレビューの Adversarial QA（破壊テスト実行）化

- **決定**: Applyフェーズの実装コードレビュー（`qa-reviewer`）において、「チェックリストを見るな。対象コードを例外終了またはアサーション失敗させるテストコードを1本書き、実際に実行せよ」と指示する。
  - テストが失敗した場合: バグ検出（`LGTM: false`）。修正ループへ。
  - テストを落とせなかった場合: 堅牢性確認（`LGTM: true`）。
- **理由**: 同一モデルによる自己レビューであっても、「攻撃モード（テスト作成・実行）」にすることで認知バイアス（追認）を破壊し、客観的な事実（実行ログ）で判定できるため。

### 3. 機械的検証の完全スクリプト委譲

- **決定**: フォーマット確認、リンター確認、テスト合否、skip放置、カバレッジしきい値チェックは、LLMレビューの項目から削除し、`verify-gate.ps1` / `verify-gate.sh` および自動コマンド実行に完全に委ねる。
- **理由**: スクリプトが1秒で100%客観判定できることをLLMに目視確認させるのは、トークンと注意力の純粋な浪費であるため。

### 4. ゲート検証スクリプトの検査ロジック改修

- **決定**: `verify-gate.ps1` および `verify-gate.sh` 内の `Assert-ReviewsValid` 関数を改修し、旧来の `Contains('✅/❌/⚠️')` 検査を廃止。
  - 新形式の各セクション（挑戦的設問への回答が空でないこと）を検証。
  - 破壊テストの実行結果ログ（Pass/Fail）が記載されていることを検証。
  - 最終判定が `- **LGTM**: true` であることを検証。

### 5. マテリアルの同期構造

- **決定**: 変更はまず `openspec-kit/`（正本）に適用し、その後同期コマンドまたは反映スクリプトを用いて `openspec/` 側に反映する。

## Risks / Trade-offs

- **[Risk] 破壊テストが書けない・不要な軽微タスク（ドキュメントや設定修正など）でのオーバーヘッド**
  → **Mitigation**: L1変更（軽微変更）や非コードタスクでは、Adversarial QA をスキップ可能（`skip_adversarial: true`）とし、悪魔の代弁者による静的確認のみで通過できるように例外規定を設ける。
- **[Risk] 破壊テストが既存テストスイートを破壊または汚染するリスク**
  → **Mitigation**: レビュアーが作成する破壊テストは、専用のスクラッチまたは一時ファイル（例: `test-scratch/` や独立テストブロック）として実行し、レビュー合意後に正式な回帰テストとして昇格させるか破棄する運用とする。

## Migration Plan

1. `openspec-kit/templates/` 配下のチェックリストテンプレートをQ&A形式へ刷新。
2. `openspec-kit/agents/` 配下のレビュアープロンプトを更新。
3. `openspec-kit/scripts/verify-gate.ps1` および `verify-gate.sh` を改修。
4. `openspec-kit/config.yaml` の運用ガイドラインを改定。
5. 本リポジトリの `openspec/` および `.agents/workflows/` へ同期。
6. `verify-gate.ps1` の自己テストを実行して回帰がないことを確認。
